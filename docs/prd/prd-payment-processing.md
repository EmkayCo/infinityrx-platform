## 1. Purpose

Payment Processing executes the payment instructions generated by the Billing module. Billing says "pay Pharmacy X $4,327.18 via Echo." This module takes that instruction, formats it for the correct vendor, submits it, tracks the response, and reports back settlement status.

This module is the adapter layer between Billing's financial logic and external payment vendors. It knows how to talk to each vendor's API/file format. Billing doesn't know vendor-specific formats. Payment Processing doesn't know billing logic. Clean separation.

**What this module does:**
- Receive payment instructions from Billing
- Format into vendor-specific files/API calls (NACHA, Echo Spec 400, Zelis API, check files)
- Submit to vendors (API, SFTP, or queue for manual pickup)
- Poll for or receive settlement confirmations
- Process ACH returns and report back to Billing
- Track payment status across all vendors in a unified view
- Manage vendor connections, credentials, and health monitoring

**What this module does NOT do:**
- Calculate payment amounts (Billing does this)
- Decide who gets paid (Billing does this)
- Generate 835 remittances (Billing does this)
- Manage invoices or AR (Billing does this)

## 3. Business Logic

### 3.1 Payment Submission Flow

1. **Receive instruction**: Billing emits `payment_batch.submitted` event with batch ID and vendor config reference
2. **Load vendor adapter**: Determine which vendor adapter to use from the billing payment batch's vendor config
3. **Format payload**: Convert billing's payment instructions into vendor-specific format:
   - **NACHA**: Generate NACHA file with correct batch/file control records, originator info from tenant's bank config, proper entry class codes. All amounts Decimal. Debits = positive with debit code.
   - **Echo Spec 400**: Generate Echo's proprietary format from payment data. Map fields per Echo specification.
   - **Zelis API**: Build JSON payload per Zelis API spec. Include all required fields.
   - **Check file**: Generate check issuance file per vendor's format. Include payee name, address, amount, remittance reference.
   - **Custom**: Use configurable field mapping to generate vendor-specific format.
4. **Validate payload**: Verify file/payload passes format validation before submission. NACHA totals match, Echo field lengths correct, Zelis required fields present.
5. **Submit**: 
   - API: POST to vendor endpoint, capture response
   - SFTP: Upload file to vendor's SFTP, verify upload success
   - Manual: Save file, notify operator for manual delivery
6. **Record submission**: Create submission record with status, file reference, vendor response
7. **Update Billing**: Emit `payment.submitted` event. Billing updates AP statuses.
8. **Start settlement tracking**: Begin polling or listening for settlement confirmations per vendor's method

### 3.2 Settlement Tracking

Per vendor's settlement method:

**API polling** (Echo, Zelis):
- Scheduled job polls vendor API at configured interval (default: hourly)
- For each pending submission, query vendor for payment status
- Match vendor responses to individual payments by vendor_payment_id or trace_number
- Update settlement_records with status, date, reference
- Report settled/returned/failed payments back to Billing via events

**Webhook** (vendors that push):
- Receive webhook at configured endpoint
- Validate webhook signature/auth
- Parse payload, match to submission and individual payments
- Update settlement_records
- Report to Billing

**File-based**:
- Operator uploads bank confirmation/settlement file
- Parser maps file format to settlement records
- Auto-match by amount + reference where possible
- Unmatched entries flagged for manual review

**Manual**:
- Operator marks individual payments as settled with date and reference
- Used for check payments where no electronic confirmation exists

### 3.3 ACH Return Handling

When an ACH return is received (from vendor API, file, or manual entry):

1. Identify the return code (R01-R85)
2. Look up default action from `ach_return_codes` table:
   - **R01 (Insufficient Funds)**: auto-retryable. Schedule retry in 3 business days (configurable).
   - **R02 (Account Closed)**: not retryable. Create carryover in Billing. Alert operator to update pharmacy bank info.
   - **R03 (No Account)**: not retryable. Create carryover. Alert.
   - **R04 (Invalid Account Number)**: not retryable. Create carryover. Alert.
   - **R08 (Payment Stopped)**: manual review. Could be disputed.
   - **R10 (Customer Advises Unauthorized)**: manual review. Potential fraud indicator — emit `fwa.payment_return_suspicious` event.
   - All others: configurable per code.
3. Update settlement_record with return code, reason, date
4. Emit `payment.returned` event to Billing with return details
5. Billing creates carryover record and handles next steps
6. If return is suspicious (R10, R29), also emit event to ReclaimRx

### 3.4 Retry Logic

For retryable failures (submission errors, transient API failures, retryable ACH returns):

1. Increment retry_count on submission
2. If retry_count < max_retries: schedule retry at next_retry_at (exponential backoff: 1hr, 4hr, 12hr — configurable)
3. If retry_count >= max_retries: mark as failed, alert operator, emit `payment.failed` event
4. Retry resubmits the same file/payload to the same vendor
5. Each retry logged in submission record

### 3.5 Vendor Health Monitoring

Scheduled health checks per vendor:

1. **API vendors**: Ping health endpoint every 5 minutes (configurable). Track response time.
2. **SFTP vendors**: Test connection every 15 minutes (configurable).
3. **Status determination**:
   - Healthy: <500ms response, no errors in last hour
   - Degraded: >500ms or 1-2 errors in last hour
   - Down: No response or >3 errors in last hour
4. Status changes trigger notifications
5. If vendor is down when a submission is due: queue the submission, alert operator, auto-submit when vendor recovers
6. Health history available for SLA tracking

### 3.6 Payee Enrollment Management

For vendors like Echo and Zelis that require pharmacies to be enrolled before receiving electronic payments:

1. When a payment is routed to a vendor for a pharmacy that is `not_enrolled`, the payment still processes but defaults to the vendor's fallback method (typically paper check or virtual card)
2. System tracks enrollment status per pharmacy per vendor
3. Enrollment workflow: system can submit enrollment request to vendor API (if vendor supports it), or flag for manual enrollment
4. When enrollment completes, future payments use the pharmacy's preferred method
5. Report: list of unenrolled pharmacies receiving payments — opportunity to convert to electronic for cost savings

### 3.7 Idempotency / Duplicate Submission Prevention
- Every submission gets a unique idempotency key derived from: tenant_id + payment_batch_id + vendor_adapter_id + submission timestamp.
- Before submitting, check if a submission with the same billing_payment_batch_id and vendor_adapter_id already exists with status != `failed`.
- If exists: do NOT resubmit. Return the existing submission record.
- Prevents double-payment if the system crashes mid-submission or an operator accidentally triggers twice.
- For API vendors: include idempotency key in the API request header (most payment APIs support this).

### 3.8 Payment File Encryption
- All generated payment files (NACHA, Echo 400, check files) encrypted at rest using AES-256.
- NACHA files contain bank routing and account numbers — classified as sensitive financial data.
- Encryption key managed by Azure Key Vault (production) or local key file (development).
- Files decrypted only at the moment of submission to the vendor.
- SFTP transfers use SSH encryption in transit. API transfers use TLS 1.3.
- Stored files in core.files marked with `is_encrypted = true` and `encryption_key_ref`.

### 3.9 Vendor Failover
- Configurable failover chain per payment route. Example: Echo (primary) → Zelis (secondary) → direct ACH (tertiary).
- If primary vendor is DOWN (per health monitoring): automatically route to next vendor in the failover chain.
- If primary vendor submission FAILS after retries: offer operator the option to reroute to failover vendor.
- Failover does NOT happen silently for settled payments — only for new submissions when the primary is unavailable.
- Failover events logged and alerted so operators know payments went through an alternate path.

### 3.10 Positive Pay Integration
- For check issuance: generate a positive pay file listing all checks issued in a batch.
- Format: configurable per bank (CSV or fixed-width with check number, amount, payee, date, account number).
- Delivery: SFTP to bank or bank portal API.
- Exception handling: if bank reports a positive pay exception (check presented but not on file), create alert for operator review.

### 3.11 Payment Reconciliation Dashboard
- Interactive reconciliation screen: expected payments (from submitted batches) vs actual settlements (confirmed by vendor/bank).
- Show: matched (expected = actual), discrepancies (expected ≠ actual), unmatched (expected but no actual, or actual but no expected).
- Drill-down: click any discrepancy to see batch details, individual payments, vendor responses.
- Age tracking: how long has each unmatched payment been outstanding?
- Export: reconciliation report as Excel for accounting review.

### 3.12 Payment Notification to Payee
- When a payment batch is submitted, generate notifications to each pay-to entity:
  - Email notification with: amount, claim count, expected settlement date, payment method. NO bank details or PHI.
  - Portal notification in pharmacy portal (Module 20b).
- Configurable per tenant: enabled/disabled, email template, portal notification toggle.
- Notification template supports tenant branding (white-label).

### 3.13 Performance Requirements
- Payment file generation: <60 seconds per batch (up to 10,000 payments)
- Vendor API submission: <30 seconds per call
- Settlement polling: <5 seconds per poll cycle per vendor
- ACH return processing: <1 second per return record

### 3.14 Data Retention
- Submission records and settlement records retained per tenant's data retention policy (default: 7 years).
- Payment files retained for same period (encrypted at rest).
- Vendor health logs retained for 1 year (operational data, not financial).

### 3.15 ACH Transaction Limits
- Same-day ACH: $1M per transaction limit (NACHA rule). Payments exceeding $1M auto-routed to standard (next-day) ACH.
- Standard ACH: no NACHA-imposed per-transaction limit, but banks may impose their own. Configurable per bank account.
- If a payment exceeds the configured limit: split into multiple entries (if permitted by bank) or route to alternative method (check, wire). Configurable behavior per tenant.
- Log all limit-triggered routing decisions for audit.

### 3.16 OFAC Screening
- Before submitting any payment, screen the pay-to entity against the OFAC (Office of Foreign Assets Control) SDN (Specially Designated Nationals) list.
- OFAC list refreshed on configurable schedule (default: daily).
- Any match: BLOCK payment, alert compliance team, flag entity for investigation.
- OFAC screening logged per NACHA 2026 fraud monitoring requirements.
- Combined with OIG/SAM screening from Core Platform for comprehensive sanctions coverage.

### 3.17 Business Day Calendar
- NACHA effective dates and settlement dates must be business days.
- Pre-loaded US federal holiday calendar (same as Billing module — shared calendar in Core Platform).
- Payment effective dates validated against calendar. Non-business day dates auto-shifted to next business day.
- Same-day ACH processing windows: 1:00 PM, 5:00 PM, 6:00 PM ET. System knows cutoff times and routes appropriately.
- Configurable bank-specific cutoff times (some banks have earlier cutoffs for same-day ACH).

### 3.18 NACHA 2026 Fraud Monitoring Compliance
- As an ACH originator, the platform must implement risk-based fraud screening on all outgoing ACH entries (effective March/June 2026).
- For every payment batch: log that fraud screening was performed (OIG/SAM check, OFAC check, payment hold check from ReclaimRx, amount reasonableness check).
- Annual review: document fraud monitoring procedures and review effectiveness. Store in compliance records.
- Company Entry Description: use correct standardized values per NACHA 2026 rules (CCD for business payments).

## 7. Events

### Published
- `payment.file_generated` — payment file created
- `payment.submitted` — file/API sent to vendor
- `payment.acknowledged` — vendor acknowledged receipt
- `payment.settled` — individual payment confirmed
- `payment.returned` — ACH return received
- `payment.failed` — submission failed after all retries
- `payment.return_suspicious` — return code suggests possible fraud (R10, R07, R29)
- `vendor.status_changed` — vendor health status changed (healthy → degraded → down)

### Consumed
- `payment_batch.submitted` — from Billing, triggers payment file generation and submission
- `fwa.payment_hold_placed` — from ReclaimRx, hold payments for specific entity
- `fwa.payment_hold_released` — from ReclaimRx, release hold

## 9. Test Scenarios (100% Coverage Required)

### Financial (100%)
- NACHA file totals match payment instruction totals (penny-perfect)
- Echo Spec 400 amounts match source data
- Settlement amounts match submission amounts
- Return amounts correctly reported back to Billing

### Critical Paths (100%)
- Full lifecycle: instruction → format → submit → acknowledge → settle → report to Billing
- ACH return: receive → identify code → apply action → report to Billing
- Retry: fail → wait → retry → succeed (or exhaust retries → alert)
- Vendor down: detect → queue → recover → auto-submit queued payments
- Payment hold: hold event → skip entity in submissions → hold released → resume

### Edge Cases
- Payment to unenrolled pharmacy — falls back to check/VCard, does not block
- Vendor API returns partial success (some payments accepted, some rejected) — handle individually
- Two submissions to same vendor overlap — no duplicate payments
- Same-day ACH enabled but bank account doesn't support it — graceful fallback to standard ACH
- Vendor health check timeout — doesn't crash, marks degraded

## 10. Session Decomposition

This module shares a session with another module in Phase 2 Batch A. Internally:

1. **Vendor adapter framework + NACHA**: adapter interface, NACHA file generator, direct ACH submission, bank file settlement parser
2. **Echo + Zelis adapters**: Echo Spec 400 generator, Echo API integration, Zelis API integration, vendor-specific settlement polling
3. **Settlement + returns + monitoring**: settlement tracking engine, ACH return processing, retry logic, vendor health monitoring, payee enrollment, payment hold integration
