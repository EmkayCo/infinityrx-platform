## WS1 — Nav Single Source of Truth

### Decision: Keep nav-config.ts as the canonical runtime source

**Justification:**

There are three nav systems:

1. `portal/operator/components/layout/nav-config.ts` — hand-authored `NAV_MODULES[]`. This is the
   live sidebar source. The `Sidebar` component and `SectionTabs` both read it directly. It is
   type-safe, Lucide-icon-typed, and already handles `findActiveModule` / `findActiveLeaf`. It
   covers all 14 top-level sections the PRD §4.1 IA requires.

2. `packages/shell/src/_generated/manifest.json` + `nav.ts` — generated by `build-manifest.ts` from
   individual `module.config.ts` `navTree` entries. Contains exactly 3 entries: Directories,
   Prescribers, PaySync. Not consumed by the portal sidebar; not integrated into `nav-config.ts`.
   This is the module-registry system for the shell loader, not the portal sidebar.

3. `packages/modules/*/module.config.ts` navTree — per-module declarations that feed the
   manifest generator.

**Why keep nav-config.ts (not switch to manifest/navTree):**

- The manifest system only knows about 3 of the 14 nav sections. Switching to it as the portal
  sidebar source would require porting 11 hand-authored sections (Claims, Programs, ReclaimRx,
  Analytics, Client Management, EDI, Network, Reporting, Network Admin, PaySync Config, Admin)
  into individual module.config.ts files — a multi-day effort with no user-visible benefit.
- nav-config.ts is already the working runtime source. Changing its source of truth would require
  rewiring the Sidebar component, which adds regression surface with zero functional gain.
- The manifest/navTree system serves a different purpose: it drives the shell's module-loader
  (which packages to import at runtime). The Sidebar needs the full 14-section tree with
  permission gating, icon types, and child arrays — things module.config.ts navTree was not
  designed to carry for arbitrary non-module sections.
- **Correct approach:** keep nav-config.ts as the sidebar source; keep manifest.json as the
  module-loader registry. They serve separate concerns. The "orphaned" manifest nav entries are
  not orphaned — they control which npm packages the shell loads, not which links appear in the
  sidebar.

**What stays retired:** The manifest `NAV_ENTRIES` array (only 3 entries) is not wired into the
portal Sidebar and should remain that way. It is the shell's internal module registry, not a nav
config. No change needed there.

**New redirects to add in F0 — ATOMIC EDIT (all three changes in a single commit):**

The existing `/billing/invoices` → `/accounting/invoices` redirect points at a non-existent page.
The fix requires removing the broken redirect AND adding the reverse in the same commit so no
intermediate state exists where `/billing/invoices` sends users to a dead `/accounting/invoices`
that then 404s. Both lines must land together.

```
REMOVE: /billing/invoices      → /accounting/invoices   (destination doesn't exist — broken)
ADD:    /accounting/invoices   → /billing/invoices       (covers dead nav bookmark; safe landing)
ADD:    /billing/cycles/:slug([^/]+(?<!new))  → /accounting/cycles/:slug
```

**Critical constraint on the cycles redirect — Next.js named segments catch `/billing/cycles/new`:**

Next.js redirect matching evaluates named segments (`:id`) before the filesystem, and a bare
`:id` segment matches ANY single path segment including the literal string `new`. Adding
`{ source: "/billing/cycles/:id", destination: "/accounting/cycles/:id" }` would redirect
`/billing/cycles/new` to `/accounting/cycles/new` (which does not exist), making the
BillingCycleWizard permanently unreachable.

**Fix:** Use a regex constraint to exclude the literal `new`:
```typescript
{
  source: "/billing/cycles/:slug([^/]+(?<!new))",
  destination: "/accounting/cycles/:slug",
  permanent: false,
}
```
The negative lookbehind `(?<!new)` on the character-class pattern ensures the segment `new` is
not matched. The existing `/billing/cycles/new/page.tsx` remains reachable at its current path.

**Verify in test:** The redirect test must assert that a request to `/billing/cycles/new` is NOT
redirected (returns the page, not a 307). Add this as an explicit assertion alongside the
`:slug` redirect test.

### Bug 2: UploadDropzone.tsx accept-allowlist excludes .txt / pipe-delimited

**Root cause confirmed:**

File: `packages/modules/paysync/src/surfaces/uploads/UploadDropzone.tsx` line 19:
```typescript
const ACCEPTED_TYPES = ".csv,.xlsx,text/csv,application/vnd.openxmlformats-officedocument.spreadsheetml.sheet";
```

This is missing `.txt` and `text/plain`. The PRD §7.2 Step 1 states: "Accepts: CSV, Excel,
pipe-delimited (configurable per client)." Pipe-delimited files are `.txt` or `.psv` files with
`text/plain` MIME type. The browser's file picker (and drag-and-drop handler) uses the `accept`
attribute to filter; `.txt` files are blocked at the client level.

**Fix:**

File: `packages/modules/paysync/src/surfaces/uploads/UploadDropzone.tsx`

Change line 19:
```typescript
const ACCEPTED_TYPES =
  ".csv,.xlsx,.txt,.psv," +
  "text/csv," +
  "text/plain," +
  "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet";
```

Also update the `aria-label` on the hidden file input (line 82) to reflect the new accepted

### Bug 3: Large-CSV upload 400s — F0 partial guard only; real fix is F1

**What F0 does NOT fix:** F0 does not solve the large-CSV body-size problem. There is no
App Router equivalent of the Pages Router `bodyParser: { sizeLimit: "50mb" }` config — that
syntax does not exist in Next.js App Router and must not be referenced. `maxDuration` is a
serverless function *timeout* setting, not a body-size limit; adding it would not change the
maximum upload size by one byte.

**What actually constrains upload size today:**
- The upload route calls `request.formData()` which buffers the entire multipart body in
  the Next.js process before passing it to the billing backend. This double-buffering is the
  source of the problem, not a missing config knob.
- In the Edge runtime, `formData()` on large bodies fails because Edge has a hard 4 MB request
  body cap enforced by the runtime, independent of any app configuration.
- In the Node.js runtime (local dev, Azure Functions), no framework-level size cap exists for
  App Router route handlers, but the full-body buffer in `formData()` + `arrayBuffer()` still
  means the entire file lives in memory twice before the backend receives it.

**F0 action — Edge-deployment guard only:**

Add a single export to `portal/operator/app/api/paysync/uploads/route.ts`:
```typescript
export const runtime = "nodejs";  // Guard: Edge runtime hard-caps at 4MB; Node.js has no such cap
```

This prevents the route from ever being deployed to an Edge function (where uploads would
silently fail at 4 MB). It does NOT raise any size limit — it merely ensures the route always
runs in the Node.js environment where no framework cap applies. This is the only meaningful
thing F0 can do for this bug without refactoring the handler.

**F0 does NOT add `export const maxDuration`.** That is a timeout setting unrelated to size.

**F1 action — streaming passthrough (the real fix):**

Refactor the POST handler to stop calling `request.formData()` / `arrayBuffer()`. Instead:
1. Parse only the metadata headers (filename from `Content-Disposition`) without buffering.
2. Pipe `request.body` (a `ReadableStream<Uint8Array>`) directly to the billing backend via a
   streaming `fetch()` POST.
3. `createRealUploadsClient.create()` in `real.ts` already accepts
   `ReadableStream<Uint8Array>` (see the stream-consumption path at lines 175-191 of `real.ts`).
   The F1 refactor wires the BFF to pass the stream through instead of a fully-buffered Blob.

This eliminates double-buffering entirely and removes any practical size constraint on uploads.
This is an F1 task because it requires refactoring the multipart parsing logic, which carries
its own regression surface and needs dedicated test coverage.

**Commit:** WS3-C2 (adds `export const runtime = "nodejs"` to uploads route.ts — 1 line).

**Regression test:**

File: `portal/operator/app/api/paysync/uploads/__tests__/route.test.ts` (or existing test file).

Add:
- Import-level assertion: the route module exports `runtime` equal to `"nodejs"`.
- Do NOT test for `maxDuration` (not added in F0).

Note: A test for the actual body-size behavior requires a real Next.js server and a large file
fixture — that belongs in F1 alongside the streaming refactor.

### Bug 4: Upload-list GET 403 — session field missing (investigate-first)

**The 403 originates from `resolveSession()` in `portal/operator/lib/bff.ts`**, not from the
billing backend. The BFF converts upstream errors to 502; a 403 reaching the browser means
`resolveSession()` returned it directly. It returns 403 in exactly two cases:
1. `INCOMPLETE_SESSION` — `!jwt || !tenantId || !userId` (one of the three session fields is
   undefined at read time).
2. `TENANT_CLAIM_MISMATCH` — `session.tenant_id` ≠ `JWT.tid` decoded from the bearer token.

**Step 0 — read the log before writing any code:**

The `logBff("session_incomplete", { has_jwt, has_tenant_id, has_user_id })` call at bff.ts
lines 97-108 already fires on every INCOMPLETE_SESSION 403. Check the Next.js server console
when the 403 occurs. The log tells you exactly which field is `undefined`. Do not write a fix
until you know which field is missing.

**Candidate root causes (in priority order of likelihood):**

**Candidate A — Auth.js v5 cookie overflow drops `access_token`.**
The NextAuth session JWT is stored in a cookie. Auth.js v5 (used in this codebase) splits the
session cookie across multiple `__Secure-authjs.session-token.N` chunks when the payload exceeds
~4 KB. If the billing backend's `access_token` (a signed JWT itself, potentially 1-2 KB) pushes
the session cookie over the chunk limit, Auth.js may fail to reassemble it and return an
incomplete session object — `access_token` becomes `undefined`. Check cookie size in browser
DevTools Network tab on a 403 request.

**Candidate B — JWT callback doesn't propagate `access_token` on token refresh.**
`auth.ts` lines 296-320 attempt a token refresh when the access token is within 60 seconds of
expiry. On a successful refresh, `token.access_token` is updated. On a failed refresh,
`token.error = "RefreshAccessTokenError"` is set but `token.access_token` is left as whatever
it was — which could be stale or undefined if the original token was never stored. If the user's
session hits the refresh window and the refresh fails (core-platform is unreachable in dev), the
next `resolveSession()` call gets `access_token: undefined`.

**Candidate C — Missing next-auth.d.ts type augmentation (hygiene, not the runtime fix).**
TypeScript type augmentation (`declare module "next-auth" { interface Session { access_token } }`)
is a compile-time concern only. It does not affect what Auth.js serialises into or reads from the
session cookie at runtime. Adding `next-auth.d.ts` is correct housekeeping and should be done,
but it will NOT fix a runtime 403 on its own. Do not conflate the two.

**Candidate D — Dead middleware interaction.**
With `proxy.ts` not running as middleware, no `x-ifx-authenticated` header is set on requests.
If any Server Component or layout reads this header to gate rendering and falls through to an
error state that looks like a 403, that would be an indirect symptom. Less likely than A or B
but worth ruling out once the middleware status is resolved (WS3-C0).

**Investigation protocol for the execute agent:**

```
1. Reproduce the 403. Open browser DevTools → Network tab.
2. Find the failing GET /api/paysync/uploads request.
3. Check the response body: { error: { code: "INCOMPLETE_SESSION" | "TENANT_CLAIM_MISMATCH" } }
4. Check the Next.js server console for the corresponding logBff() line.
   - If "session_incomplete": note which of has_jwt / has_tenant_id / has_user_id is false.
     → false has_jwt → Candidate A (cookie overflow) or Candidate B (refresh failure).
     → false has_tenant_id or has_user_id → different serialization issue.
   - If "session_jwt_tenant_mismatch": → Candidate B variant (refresh returns different tenant).
5. In browser DevTools → Application → Cookies: check for __Secure-authjs.session-token cookies.
   If you see multiple numbered chunks (…token.0, …token.1), cookie overflow is confirmed (A).
6. Based on finding, apply the targeted fix (see below).
```

**Fixes by candidate:**

- **Candidate A (cookie overflow):** Reduce session cookie payload. The `refresh_token` field is
  stored in the session cookie but never needed client-side. Remove `token.refresh_token` from
  the `jwt()` callback's session pass-through, or move it to a server-side store (httpOnly
  cookie or Redis). The `access_token` is the only bearer credential `resolveSession()` needs.
- **Candidate B (refresh failure):** Add a guard in the JWT callback: if the refresh response is
  not ok and `token.access_token` is falsy, set `token.error = "RefreshAccessTokenError"` and
  do NOT clear the existing token. Ensure `resolveSession()` treats a stale-but-present
  `access_token` as usable rather than failing with INCOMPLETE_SESSION on a missing value.
- **All candidates:** Add `next-auth.d.ts` type augmentation as hygiene regardless of which
  candidate is the runtime cause. This prevents TypeScript from flagging the custom session
  fields as errors and documents the session shape for future maintainers.

**`next-auth.d.ts` content (hygiene — add regardless of root cause):**

```typescript
import "next-auth";

declare module "next-auth" {
  interface Session {
    access_token?: string;
    error?: string;
    mfa_required?: boolean;
    mfa_challenge_token?: string;
  }
  interface User {
    tenant_id?: string;
    permissions?: string[];
    role?: string;
    mfa_enrolled?: boolean;
    access_token?: string;
    refresh_token?: string;
    expires_at?: number;
    mfa_required?: boolean;
    mfa_challenge_token?: string;
  }
}

declare module "next-auth/jwt" {
  interface JWT {
    id?: string;
    role?: string;
    tenant_id?: string;
    permissions?: string[];
    mfa_enrolled?: boolean;
    access_token?: string;
    refresh_token?: string;
    expires_at?: number;
    error?: string;
    mfa_required?: boolean;
    mfa_challenge_token?: string;
  }
}
```

**Commit:** WS3-C3 — investigation-driven fix (exact file depends on root cause found) +
`next-auth.d.ts` type hygiene as a separate, always-safe change.
